# UX optimization

| Flow | Original behavior / friction | Change | Expected benefit | Measurement |
|---|---|---|---|---|
| Move between Library, Gallery, Vault and Settings while changing Duo width | `horizontalSizeClass` selected between a plain compact content view with a custom inset and a separate native regular `TabView`. | On iOS 26+, use one `.sidebarAdaptable` `TabView` with system compact accessory and sidebar action. | Avoids replacing the navigation container during a resize and delegates Duo bar placement to the system. | No tap-count or latency benchmark has been run; state continuity remains pending simulator/UI validation. |
| Scan from compact navigation | A custom fixed-height bar held Scan in the center and four tabs in a horizontal row. | Put Scan in `tabViewBottomAccessory`; keep the sidebar action for regular presentation. | Consistent system chrome, including system-selected compact/vertical placement. | Existing `tab.capture` UI coverage is pending execution on the required simulators. |
| Edit a document in a regular-width viewport | The app always allocated a page rail (when multi-page), canvas and inspector HStack; narrow regular widths had no fallback. | Compact workspace below measured proposal thresholds; split canvas and inspector with `ArrangementView` on iOS 27.1+. | Preserves a usable canvas when space is limited and uses the Duo division for the existing peer regions on wide screens. | The thresholds are layout guardrails, not measured performance or user research. Visual validation is pending. |
| Keep editor controls and menus clear of the Duo trailing rail | The user-provided 2026-10-21 screenshot showed editor content close to the system rail. A placement test measured a `More` menu row at x=442 pt, crossing the 382 pt content boundary. | Keep the system vertical toolbar enabled; host the compact `More` menu beside document metadata in the content area. The canvas, style carousel, zoom and bottom toolbar continue to follow the safe content region. | Leaves the rail for system widgets and native toolbar actions while keeping app menu choices in the editor content. | Verified on iPhone Duo/iOS 27.1 with closed-pose bounds and menu reachability; `testDuoClosedEditorKeepsContentInsideTheSafeArea` and `testDuoEditorActionsAndToolsStayInTheirAdaptiveRegions` passed. Dynamic Type remains outside this focused check. |
| Change editor presentation while editing | The inspector's selected tab was local state in a subview that disappeared in compact mode. | Lift inspector selection into `EditorView` and bind it into the inspector. | Reopening expanded mode returns to the chosen inspector section. | Code-level continuity change; needs a resize-in-flow UI test and runtime check. |
| Read the legacy compact tab row with larger text | The fallback row used a fixed 10 pt label and fixed-height bar. | Scale the label with Dynamic Type; at accessibility text sizes, leave the icon with its existing VoiceOver label. | Prevents tiny tab labels and avoids squeezing enlarged text into the fixed bar. | No accessibility-size simulator pass has been run yet. |
| Browse Library or choose a capture/import source on a folded display | The two-column regular layout kept only an 8/18 pt gap and did not query the vertical reserved division. | Add the active vertical division width to the inter-column gutter; use the original one-column order at accessibility text sizes. | Keeps peer columns on either side of an active hinge and keeps large text readable. | Needs open/partial-fold and accessibility Dynamic Type checks in Device Hub. |

No task-time, navigation-tap, scroll-distance, CPU, memory, or animation measurements were collected. Benefits above are the expected effect of the code changes, not measured outcomes.
